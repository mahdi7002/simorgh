# اصول ساخت سیمرغ — الزام‌آور برای هر AI یا انسانی که روی این پروژه کار می‌کند

این سند مکمل `AI_WORK_CONTRACT.md` است، نه جایگزین آن. نقض هر بند زیر یعنی توقف کار و گزارش به مهدی، نه ادامه‌دادن با توجیه.

## قانون ۱ — یک ریپو، بدون استثنا
هیچ کپی دوم از این پروژه (به هر اسمی: simorgh-vX, simorgh_backup, simorgh-sync, ...) هرگز ساخته نمی‌شود. اگر نیاز به آزمایش ایده‌ای هست، یک برنچ در همین ریپو ساخته می‌شود، نه یک کلون جدا. قبل از git clone یا cp -r از این ریپو به هر مسیر دیگر، AI باید متوقف شود و از مهدی بپرسد.

شاهد لازم اگر این قانون شکسته شد: چرا یک برنچ کافی نبود؟

## قانون ۲ — عمق قبل از عرض
هیچ قابلیت جدید (پرسونا، حوزه‌ی دانش، ابزار) وارد مسیر زنده (core/chat.py, dashboard, API عمومی) نمی‌شود مگر:
۱. یک benchmark مستقل روی حداقل ۵۰ نمونه‌ی واقعی اجرا شده باشد
۲. دقت/پوشش ثبت و در یک فایل EVIDENCE.md کنار همان ماژول مستند شده باشد
۳. نتیجه به مهدی گزارش و تأیید شده باشد

وصل‌کردن یک قابلیت تست‌نشده به مسیر زنده، حتی موقت، مجاز نیست.

## قانون ۳ — مدل = مهمان، نه صاحب‌خانه
هیچ پاسخی که از retrieval قطعی (دیتابیس، FTS، قوانین) قابل استخراج است، به مدل زبانی واگذار نمی‌شود. مدل فقط برای روایت/لحن استفاده می‌شود، نه تولید محتوای قابل‌استناد. اگر پاسخی باید از منبع بیاید و منبع چیزی برنگرداند، پاسخ صریحاً می‌گوید «پیدا نشد» — هرگز مدل جایگزین غیاب منبع نمی‌شود.

## قانون ۴ — هیچ ساب‌سیستم خودمختار جدیدی قبل از پایداری فعلی
هیچ لایه‌ی ناظر/خودمختار جدید (شبیه Mother، agent جدید، orchestrator جدید) ساخته نمی‌شود مگر:
۱. تمام ساب‌سیستم‌های موجود از این دسته حداقل ۲ هفته بدون incident باز روی main کار کرده باشند
۲. برنچ آن ساب‌سیستم موجود، صفر فاصله‌ی commit با main داشته باشد

## قانون ۵ — هر دامنه، ریپوی خودش
EarthOS، کتابخانه، ویور معماری، ماژول قرآن، یا هر پروژه‌ی مستقل دیگر، هرگز داخل ریپوی simorgh قرار نمی‌گیرد. فقط به‌عنوان سرویس مجزا می‌تواند به Mother یا به API سیمرغ وصل شود.

scripts/ai_session_start_check.sh
